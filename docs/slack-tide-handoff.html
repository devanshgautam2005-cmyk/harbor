The activity-triggered cue, specced for engineering — pipeline, data requirements, screens, guardrails, and where the real platform risk sits. Written for whoever picks this up next, not just the design side.

2Context, briefly

Slack Tide is a trigger source, not a standalone feature. It watches for a personal "slack tide" — the still moment after walking stops or a scroll session ends — and uses it to surface a low-friction, three-way prompt to call a parent. It feeds the same Logged ledger the rest of Harbor's Dispatch pipeline already writes to. Full design rationale and gate analysis live in the two earlier documents (signal-check, slack-tide-pipeline); this doc is the buildable version of that thinking.

3Pipeline spec

Nine stages. Ability/Timing gates are already handled by design; this table exists to make each stage's input and output explicit for implementation.

4Platform & data feasibility

This is the part worth reading before estimating. Two things named in the original concept need a substitution or a spike before they're buildable as described.

SignalAndroidiOS
Walking → still buildable now
Activity Recognition Transition API (Google Play services location/activity APIs). This is a separate API from Google Fit — not affected by the Fit shutdown.		 buildable now
Core Motion's activity manager gives the same walking/stationary detection natively, no third-party dependency.
"Google Fit" as named in the concept do not build against this
Google is retiring the Google Fit APIs (including the REST API) by end of 2026; new sign-ups have been closed since May 2024. The walking signal above doesn't actually need Fit at all — the Activity Recognition Transition API is independent of it. If step-history data is wanted elsewhere in Harbor later, that's Health Connect (Android 14+), a separate build.
App-session-length proxy (Instagram stand-in) straightforward
UsageStatsManager reads per-app foreground time directly in-app.		 needs a spike
DeviceActivity (FamilyControls extension) can fire a threshold callback ("Instagram used N minutes") without exposing raw usage to the main app — good enough for a trigger. But it requires the user to hand-pick the app via an opaque token, needs a separate extension target, and documented reports show monitoring schedules degrading past ~45 minutes and under thermal load. Needs its own fallback before it's reliable enough to ship.
Literal reel-watch count not exposed
Instagram/Meta has no public API surface for reel-consumption counts on either platform. Session duration is the real substitute, not a temporary one.

5Data model

shared ledger entry — written at stage 9, read by stage 3 and by Jar/Wrapped
LedgerEntry { user_id: string date: "YYYY-MM-DD" trigger_source: "walking_stop" | "session_end" | "manual" threshold_snapshot: { walking_minutes: number, session_minutes: number } resolution: "called" | "reacted" | "proposed_later" | "dismissed" proposed_time: timestamp | null feedback_pulse: "good_time" | "bad_time" | null reward_shown: "readout" | "jar_fill" | "wrapped_clip" | null }
per-user settings — editable any time, not just at onboarding
UserThresholds { walking_minutes: number // user-calibrated; ship a suggested default, never lock it session_minutes: number daily_cap: number // guardrail — max cues per day cooldown_minutes: number // guardrail — min gap between cues }

6Screens needed for MVP

  • Permission & privacy explainer — shown before requesting activity/usage-access permission; states plainly that data stays on-device and is never shared with a parent
  • Threshold calibration — first-run default, editable later from settings
  • Cue sound picker — parent's ringtone or a chosen song
  • Cue surface — full-screen, always dismissible in one gesture
  • Resolution screen — call now / react / propose later, equal weight
  • Reward moment — inline, not a separate screen; three visual variants (readout / Jar fill / Wrapped clip)
  • Feedback pulse — one tap, shown once per resolution
  • Settings — edit thresholds, sound, view current cap/cooldown

7Guardrails

Non-negotiables carried over from the design rationale — these aren't style preferences, each one maps to a specific gate risk from the earlier audit.

do

  • Keep a real, no-cost dismiss on every cue surface
  • Let the user set their own threshold
  • Cap daily frequency and suppress once logged
  • Fire only on the stop transition, never mid-activity
  • State the privacy boundary on the cue screen itself

don't

  • Force a binary choice (no true opt-out)
  • Hardcode a threshold as a product default
  • Share activity data with a parent, ever
  • Use streak mechanics or a breakable chain
  • Make the reward random rather than varying-but-guaranteed

8Open questions for engineering

iOS session-trigger reliability Run a feasibility spike on DeviceActivity threshold callbacks specifically past the ~45-minute mark and under thermal throttling before committing the session-based trigger to any release.
Android walking-data architecture Decide whether Health Connect is needed at all for Slack Tide, or whether the Activity Recognition Transition API alone is sufficient — Health Connect only matters if step history is wanted elsewhere in Harbor.
Permission consent copy Activity and usage-access permissions read as sensitive to most people; the explainer screen's copy needs a privacy pass before this ships, not after.
Degraded mode If activity/usage permission is denied or revoked, does Slack Tide fall back to a manual context-prompt version, or switch off entirely? Needs a decision, not a default arrived at by omission.

9Phasing

v0.1 — mvp
Android only. Walking-stop trigger only — skip the session-based trigger entirely for this release, since it's the platform-harder half. Full three-way resolution, user-set threshold, frequency cap, feedback pulse, reward readout. Logged into existing Dispatch/Jar.
v0.2
Add the app-session trigger — Android via UsageStatsManager first (straightforward), iOS gated behind the DeviceActivity spike above.
v0.3
iOS walking trigger via Core Motion. Opt-in Tribe reward layer. Wrapped-clip reward variant.
